# Día 7: Subqueries - El Arte de Pensar en Capas

## 1. Objetivo del Día

Dominar las subqueries en todas sus formas: no correlacionadas, correlacionadas, en WHERE, en FROM (derived tables), en SELECT (scalar subqueries). Al final de este día, sabrás cuándo una subquery es la herramienta correcta vs un CTE o un JOIN, y cómo escribir subqueries que un optimizer pueda transformar en ejecuciones eficientes.

## 2. Teoría: Subqueries como Staff Engineer

### ¿Qué es una subquery?

Una subquery es una consulta anidada dentro de otra consulta. Parece simple, pero es una de las herramientas más poderosas -- y más mal utilizadas -- en SQL.

```sql
SELECT name, price
FROM inventory.products
WHERE category_id IN (
    SELECT id 
    FROM marketing.categories 
    WHERE name = 'Electronics'
);
```

### Las 4 Formas de Usar Subqueries

#### 1. Subquery No Correlacionada (Scalar / Multi-row)

Se ejecuta UNA SOLA VEZ, independientemente de la consulta externa. El optimizer la resuelve primero y pasa el resultado al query principal.

```sql
-- Scalar: devuelve un solo valor
SELECT name, salary
FROM hr.employees
WHERE salary > (
    SELECT AVG(salary) FROM hr.employees
);

-- Multi-row (IN): devuelve un conjunto
SELECT name, price
FROM inventory.products
WHERE supplier_id IN (
    SELECT id FROM core.suppliers WHERE category_focus = 'Electronics'
);
```

**Performance:** Excelente. El optimizer la ejecuta una vez y cachea el resultado.

#### 2. Subquery Correlacionada

Se ejecuta UNA VEZ POR CADA FILA de la consulta externa. La subquery referencia columnas de la tabla externa.

```sql
-- Para cada empleado, encontrar el salario máximo de SU departamento
SELECT 
    e.first_name,
    e.last_name,
    e.salary,
    (SELECT MAX(e2.salary) 
     FROM hr.employees e2 
     WHERE e2.department_id = e.department_id) AS dept_max_salary
FROM hr.employees e;
```

**Performance:** Potencialmente costosa. Se ejecuta N veces (una por fila externa). Pero el optimizer moderno puede convertirla en un JOIN internamente.

#### 3. Derived Table (Subquery en FROM)

La subquery se materializa como una "tabla virtual" que el query externo trata como cualquier otra tabla.

```sql
SELECT 
    dept.department_name,
    dept.total_salary,
    emp.first_name,
    emp.salary
FROM (
    SELECT 
        d.id,
        d.name AS department_name,
        SUM(e.salary) AS total_salary
    FROM hr.departments d
    JOIN hr.employees e ON e.department_id = d.id
    GROUP BY d.id, d.name
) dept
JOIN hr.employees emp ON emp.department_id = dept.id
WHERE emp.salary > dept.total_salary / 10;
```

**Performance:** PostgreSQL puede materializarla o inline-earla dependiendo de complejidad.

#### 4. Subquery en EXISTS / NOT EXISTS

Ya la vimos el Día 3. Es la forma más eficiente para verificar existencia sin traer datos.

```sql
SELECT c.first_name, c.last_name
FROM core.customers c
WHERE EXISTS (
    SELECT 1 
    FROM sales.orders o 
    WHERE o.customer_id = c.id 
        AND o.status = 'Delivered'
);
```

### Jerarquía de Decisión: Subquery vs CTE vs JOIN

| Escenario | Herramienta Correcta |
|-----------|---------------------|
| Filtrar por un valor agregado global | Subquery scalar en WHERE |
| Filtrar por existencia | EXISTS / NOT EXISTS |
| Filtrar por conjunto de valores | IN (subquery) |
| Resultado reutilizable 2+ veces | CTE |
| Lógica compleja que necesita nombre | CTE |
| Comparar fila a fila con otra tabla | JOIN |
| Calcular algo por fila basado en contexto externo | Subquery correlacionada |
| Top-N por grupo | Window Function (no subquery) |

**Regla del Staff Engineer:** Si puedes resolverlo con un JOIN o una Window Function, NO uses subquery correlacionada. Las subqueries correlacionadas son el último recurso cuando JOINs y windows no expresan la lógica de forma natural.

### Subqueries y el Optimizer de PostgreSQL

PostgreSQL tiene un optimizer sofisticado que puede:

1. **Pull up:** Convertir una subquery en FROM en un JOIN
2. **Push down:** Mover filtros de la query externa hacia la subquery
3. **Decorrelate:** Convertir subqueries correlacionadas en JOINs
4. **Materialize vs Inline:** Decidir si materializa la derived table o la evalúa en cada acceso

**Lo que NO puede hacer:** Si usas `LIMIT` o `OFFSET` en una subquery, o si la subquery tiene side effects (funciones volátiles), el optimizer está forzado a ejecutarla tal cual.

```sql
-- El optimizer NO puede decorrelar esto porque LIMIT fuerza materialización
SELECT *
FROM inventory.products p
WHERE p.id IN (
    SELECT product_id 
    FROM sales.order_items oi
    ORDER BY oi.quantity DESC
    LIMIT 10
);
```

## 3. Mentalidad de Data Engineer

### Cómo piensa un profesional con subqueries

**1. Primero pregunta: "¿esto se puede resolver sin subquery?"**

Junior: "Voy a hacer una subquery para todo"

Staff: "¿Esto es un JOIN disfrazado? ¿Es una window function?"

**2. Piensa en cardinalidad antes de escribir**

Antes de escribir una subquery correlacionada, pregúntate:
- ¿Cuántas filas tiene la tabla externa?
- ¿Cuántas veces se ejecutará la subquery?
- ¿Hay un índice que soporte la correlación?

Si la tabla externa tiene 500K filas y la subquery tarda 1ms, son 500 segundos. Un JOIN tardaría 2 segundos.

**3. Subquery scalar vs JOIN: no es lo mismo**

```sql
-- MAL si hay muchos empleados: subquery se ejecuta N veces
SELECT 
    e.first_name,
    (SELECT d.name FROM hr.departments d WHERE d.id = e.department_id) AS dept_name
FROM hr.employees e;

-- BIEN: JOIN es una sola operación
SELECT 
    e.first_name,
    d.name AS dept_name
FROM hr.employees e
JOIN hr.departments d ON d.id = e.department_id;
```

**4. La subquery en SELECT solo debe devolver UN valor**

Si una subquery scalar devuelve más de una fila, PostgreSQL lanza un error. Siempre valida cardinalidad.

**5. Derived tables pierden contexto de índices**

Cuando pones una subquery en FROM, PostgreSQL puede materializarla (crear una tabla temporal en memoria). Si la derived table es grande, pierdes la capacidad de usar índices de las tablas originales.

```sql
-- MAL: derived table gigante, pierde índices
SELECT *
FROM (
    SELECT o.*, c.first_name, c.last_name
    FROM sales.orders o
    JOIN core.customers c ON c.id = o.customer_id
) sub
WHERE sub.order_date >= '2025-01-01';

-- BIEN: filtrar ANTES de join, o simplemente hacer el JOIN directo
SELECT o.*, c.first_name, c.last_name
FROM sales.orders o
JOIN core.customers c ON c.id = o.customer_id
WHERE o.order_date >= '2025-01-01';
```

## 4. Ejemplos Prácticos

### Ejemplo 1: Clientes que compraron en todas las categorías (división relacional)

```sql
-- Objetivo: Encontrar clientes que han comprado productos de TODAS las categorías activas
-- Esto es un problema de "división relacional" -- clásico en entrevistas FAANG

SELECT 
    c.id AS customer_id,
    c.first_name || ' ' || c.last_name AS full_name,
    c.email,
    COUNT(DISTINCT p.category_id) AS categories_purchased
FROM core.customers c
JOIN sales.orders o ON o.customer_id = c.id
JOIN sales.order_items oi ON oi.order_id = o.id
JOIN inventory.products p ON p.id = oi.product_id
WHERE o.status <> 'Cancelled'
GROUP BY c.id, c.first_name, c.last_name, c.email
HAVING COUNT(DISTINCT p.category_id) = (
    SELECT COUNT(*) FROM marketing.categories WHERE parent_id IS NOT NULL
)
ORDER BY full_name;
```

**Análisis:**
- Subquery scalar en HAVING: cuenta total de subcategorías
- La subquery NO está correlacionada -- se ejecuta una sola vez
- `COUNT(DISTINCT p.category_id)` cuenta cuántas categorías diferentes ha comprado cada cliente
- HAVING compara contra el total: si coinciden, compró en TODAS

### Ejemplo 2: Empleados que ganan más que el promedio de su departamento + ranking

```sql
-- Objetivo: Para cada departamento, mostrar empleados que ganan más que el promedio
-- del departamento, junto con la diferencia y su posición relativa

SELECT 
    d.name AS department_name,
    e.first_name || ' ' || e.last_name AS full_name,
    e.job_title,
    e.salary,
    dept_stats.dept_avg,
    ROUND(e.salary - dept_stats.dept_avg, 2) AS diff_vs_avg,
    (SELECT COUNT(*) + 1
     FROM hr.employees e2
     WHERE e2.department_id = e.department_id
       AND e2.salary > e.salary
       AND e2.is_active = TRUE
    ) AS salary_rank_in_dept
FROM hr.employees e
JOIN hr.departments d ON d.id = e.department_id
JOIN (
    SELECT 
        department_id,
        AVG(salary) AS dept_avg
    FROM hr.employees
    WHERE is_active = TRUE
    GROUP BY department_id
) dept_stats ON dept_stats.department_id = e.department_id
WHERE e.is_active = TRUE
    AND e.salary > dept_stats.dept_avg
ORDER BY d.name, e.salary DESC;
```

**Análisis:**
- Derived table `dept_stats`: calcula promedio por departamento una sola vez
- Subquery correlacionada en SELECT: calcula ranking salarial (cuántos ganan más que este empleado)
- La subquery correlacionada es aceptable aquí porque el ranking por "count of higher salaries" no se expresa naturalmente con window functions si queremos saltar posiciones como RANK()
- Alternativa profesional: usar `RANK() OVER (PARTITION BY department_id ORDER BY salary DESC)` en lugar de la subquery correlacionada

### Ejemplo 3: Análisis de productos con múltiples subqueries para detección de anomalías de pricing

```sql
-- Objetivo: Detectar productos cuyo precio está significativamente desviado
-- del promedio de su categoría, considerando solo productos activos

SELECT 
    p.name AS product_name,
    p.sku,
    p.price,
    p.cost,
    ROUND(p.price - p.cost, 2) AS margin,
    cat_avg.avg_price AS category_avg_price,
    ROUND(p.price - cat_avg.avg_price, 2) AS diff_vs_category,
    ROUND(
        (p.price - cat_avg.avg_price) * 100.0 
        / NULLIF(cat_avg.avg_price, 0), 2
    ) AS pct_diff_vs_category,
    CASE 
        WHEN p.price > cat_avg.avg_price * 1.5 THEN 'OVERPRICED'
        WHEN p.price < cat_avg.avg_price * 0.5 THEN 'UNDERPRICED'
        ELSE 'NORMAL'
    END AS pricing_flag,
    (SELECT COUNT(*)
     FROM marketing.reviews r
     WHERE r.product_id = p.id
    ) AS review_count,
    (SELECT COALESCE(AVG(r2.rating), 0)
     FROM marketing.reviews r2
     WHERE r2.product_id = p.id
    ) AS avg_rating
FROM inventory.products p
JOIN (
    SELECT 
        p2.category_id,
        AVG(p2.price) AS avg_price
    FROM inventory.products p2
    WHERE p2.is_active = TRUE
    GROUP BY p2.category_id
) cat_avg ON cat_avg.category_id = p.category_id
WHERE p.is_active = TRUE
    AND (
        p.price > cat_avg.avg_price * 1.5
        OR p.price < cat_avg.avg_price * 0.5
    )
ORDER BY ABS(p.price - cat_avg.avg_price) DESC;
```

**Análisis:**
- Derived table `cat_avg`: precio promedio por categoría (no correlacionada, se ejecuta una vez)
- Dos subqueries correlacionadas en SELECT: review_count y avg_rating por producto
- Las subqueries correlacionadas son aceptables porque son simples lookups por PK (product_id) y PostgreSQL las optimiza bien
- Si la tabla de reviews fuera enorme, sería mejor convertirlas en LEFT JOIN + GROUP BY

## 5. Code Review: Consulta de Junior vs Profesional

### Consulta Junior

```sql
-- "Necesito los productos activos que nunca han recibido una review"
SELECT p.name, p.sku, p.price
FROM inventory.products p
WHERE p.id NOT IN (
    SELECT r.product_id FROM marketing.reviews r
);
```

### Análisis del Junior

**Problemas:**
1. **NOT IN con NULLs:** Si `product_id` en reviews tiene algún NULL, `NOT IN` devuelve EMPTY SET. Este es el bug más peligroso de las subqueries.
2. **No usa NOT EXISTS:** Para anti-joins, NOT EXISTS es siempre preferible a NOT IN.
3. **Sin índice:** No aprovecha índices de forma óptima.
4. **Sin contexto de negocio:** No muestra categoría, rating promedio (si existiera), ni stock actual.

### Versión Profesional

```sql
SELECT 
    p.name AS product_name,
    p.sku,
    p.price,
    c.name AS category_name,
    COALESCE(SUM(s.quantity), 0) AS current_stock,
    p.created_at::DATE AS listed_since
FROM inventory.products p
JOIN marketing.categories c ON c.id = p.category_id
LEFT JOIN inventory.stocks s ON s.product_id = p.id
WHERE p.is_active = TRUE
    AND NOT EXISTS (
        SELECT 1 
        FROM marketing.reviews r 
        WHERE r.product_id = p.id
    )
GROUP BY p.id, p.name, p.sku, p.price, c.name, p.created_at
ORDER BY p.created_at ASC;
```

**Mejoras:**
1. **NOT EXISTS en lugar de NOT IN:** Inmune a NULLs, más performante
2. **SELECT 1 en EXISTS:** No trae datos innecesarios
3. **Contexto de negocio:** Muestra categoría, stock actual, fecha de alta
4. **Solo activos:** Filtra productos que aún están en catálogo
5. **Ordenamiento útil:** Los más antiguos sin reviews primero (prioridad para incentivar reseñas)

## 6. Errores Frecuentes

### Error 1: NOT IN con NULLs -- el bug silencioso

```sql
-- MAL: Si algún product_id en order_items es NULL, esto devuelve 0 filas
SELECT name FROM inventory.products
WHERE id NOT IN (SELECT product_id FROM sales.order_items);

-- BIEN: NOT EXISTS es inmune a NULLs
SELECT name FROM inventory.products p
WHERE NOT EXISTS (
    SELECT 1 FROM sales.order_items oi WHERE oi.product_id = p.id
);

-- ALTERNATIVA: LEFT JOIN + IS NULL
SELECT p.name
FROM inventory.products p
LEFT JOIN sales.order_items oi ON oi.product_id = p.id
WHERE oi.id IS NULL;
```

### Error 2: Subquery correlacionada cuando un JOIN basta

```sql
-- MAL: Subquery correlacionada para algo que es un JOIN simple
SELECT 
    o.id,
    o.order_date,
    (SELECT c.first_name FROM core.customers c WHERE c.id = o.customer_id) AS customer_name
FROM sales.orders o;

-- BIEN: JOIN directo
SELECT 
    o.id,
    o.order_date,
    c.first_name AS customer_name
FROM sales.orders o
JOIN core.customers c ON c.id = o.customer_id;
```

### Error 3: Subquery scalar que devuelve más de una fila

```sql
-- MAL: Si un cliente tiene múltiples órdenes, esto falla con error
SELECT 
    c.first_name,
    (SELECT o.net_amount FROM sales.orders o WHERE o.customer_id = c.id) AS last_order
FROM core.customers c;

-- BIEN: Limitar a 1 fila o usar agregación
SELECT 
    c.first_name,
    (SELECT MAX(o.order_date) FROM sales.orders o WHERE o.customer_id = c.id) AS last_order_date
FROM core.customers c;
```

### Error 4: Derived table innecesaria que degrada performance

```sql
-- MAL: Derived table que fuerza materialización de toda la tabla
SELECT *
FROM (
    SELECT * FROM sales.orders
) sub
WHERE sub.status = 'Delivered';

-- BIEN: Filtrar directamente
SELECT *
FROM sales.orders
WHERE status = 'Delivered';
```

### Error 5: Subquery que podría ser un CTE (legibilidad)

```sql
-- MAL: Subquery repetida 2 veces
SELECT 
    (SELECT COUNT(*) FROM sales.orders WHERE status = 'Delivered') AS delivered,
    (SELECT COUNT(*) FROM sales.orders WHERE status = 'Cancelled') AS cancelled;

-- BIEN: CTE que calcula ambas métricas en un solo pass
WITH status_counts AS (
    SELECT status, COUNT(*) AS cnt
    FROM sales.orders
    GROUP BY status
)
SELECT 
    (SELECT cnt FROM status_counts WHERE status = 'Delivered') AS delivered,
    (SELECT cnt FROM status_counts WHERE status = 'Cancelled') AS cancelled;
```

## 7. Resumen

### Conceptos Clave

1. **Subquery no correlacionada:** Se ejecuta una vez, independiente del query externo
2. **Subquery correlacionada:** Se ejecuta por cada fila externa -- cuidado con performance
3. **Derived table:** Subquery en FROM, se trata como tabla virtual
4. **Scalar subquery:** Devuelve un solo valor (una fila, una columna)
5. **NOT EXISTS > NOT IN:** Siempre, por el problema de NULLs

### Cuándo Usar Cada Forma

| Patrón | Cuándo Usarlo |
|--------|---------------|
| Subquery scalar en WHERE | Comparar contra un valor agregado global |
| IN (subquery) | Filtrar por conjunto dinámico de valores |
| NOT EXISTS | Anti-join: filas sin correspondencia |
| Subquery correlacionada en SELECT | Cálculo por fila cuando JOIN no es natural |
| Derived table en FROM | Resultado intermedio que necesita JOIN adicional |
| CTE (en lugar de subquery) | Cuando la subquery se reutiliza o es compleja |

### Reglas de Oro

1. **NOT EXISTS > NOT IN:** Siempre, por el bug de NULLs
2. **JOIN > subquery correlacionada:** Si un JOIN expresa la misma lógica, úsalo
3. **CTE > subquery anidada:** Si la subquery es compleja o se reutiliza
4. **SELECT 1 en EXISTS:** No traigas datos que no necesitas
5. **Cuidado con derived tables grandes:** Pueden perder acceso a índices
6. **Valida cardinalidad de subqueries scalares:** Si puede devolver +1 fila, usa LIMIT 1 o agregación
