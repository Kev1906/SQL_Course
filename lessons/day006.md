# Día 6: Window Functions - El Arma Secreta del Data Engineer

## 1. Objetivo del Día

Dominar las Window Functions para realizar análisis avanzados sin colapsar filas. Al final de este día, podrás calcular rankings, acumulados, promedios móviles y comparativas entre filas relacionadas sin usar self-joins ni subconsultas correlacionadas.

## 2. Teoría: Window Functions como Staff Engineer

### ¿Qué son las Window Functions?

Las Window Functions realizan cálculos a través de un conjunto de filas relacionadas con la fila actual. A diferencia de las funciones de agregación tradicionales (GROUP BY), las window functions **no colapsan las filas**. Cada fila mantiene su identidad mientras accede a información de su "ventana" de contexto.

```sql
SELECT 
    employee_id,
    department_id,
    salary,
    AVG(salary) OVER (PARTITION BY department_id) AS dept_avg_salary,
    salary - AVG(salary) OVER (PARTITION BY department_id) AS diff_from_avg
FROM hr.employees;
```

### Anatomía de una Window Function

```sql
FUNCTION_NAME(expr) OVER (
    [PARTITION BY column1, column2, ...]
    [ORDER BY column3, column4, ...]
    [frame_clause]
)
```

**PARTITION BY:** Divide el resultado en particiones independientes. Cada partición es como un "mini GROUP BY" pero sin colapsar filas.

**ORDER BY:** Define el orden dentro de cada partición. CRÍTICO para funciones de ranking y acumulados.

**Frame clause:** Define qué filas de la partición se incluyen en el cálculo (ROWS, RANGE, GROUPS).

### Las 3 Categorías Fundamentales

#### 1. Funciones de Ranking

- `ROW_NUMBER()`: Número único secuencial (1, 2, 3, 4...)
- `RANK()`: Ranking con empates que saltan posiciones (1, 1, 3, 4...)
- `DENSE_RANK()`: Ranking con empates sin saltar posiciones (1, 1, 2, 3...)
- `NTILE(n)`: Divide en n buckets aproximadamente iguales

**Cuándo usar cada una:**
- `ROW_NUMBER()`: Cuando necesitas IDs únicos o top-N sin empates
- `RANK()`: Cuando los empates deben ocupar la misma posición pero dejar huecos
- `DENSE_RANK()`: Cuando los empates deben ocupar la misma posición sin huecos
- `NTILE()`: Para cuartiles, deciles, percentiles

#### 2. Funciones de Offset

- `LAG(expr, offset, default)`: Valor de la fila anterior (o N filas atrás)
- `LEAD(expr, offset, default)`: Valor de la fila siguiente (o N filas adelante)
- `FIRST_VALUE(expr)`: Primer valor del frame
- `LAST_VALUE(expr)`: Último valor del frame
- `NTH_VALUE(expr, n)`: N-ésimo valor del frame

**Casos de uso típicos:**
- Comparar mes actual vs mes anterior (LAG)
- Calcular días entre eventos consecutivos (LAG/LEAD con fechas)
- Encontrar el primer/último valor en una serie temporal

#### 3. Funciones de Agregación como Window

CUALQUIER función de agregación puede usarse como window function:
- `SUM() OVER (...)`: Acumulado running total
- `AVG() OVER (...)`: Promedio móvil o comparativa
- `COUNT() OVER (...)`: Conteo acumulativo
- `MIN()/MAX() OVER (...)`: Mínimo/máximo en ventana

### El Frame Clause: Donde la Magia Ocurre

```sql
SUM(amount) OVER (
    PARTITION BY customer_id 
    ORDER BY order_date 
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

**Opciones de frame:**
- `UNBOUNDED PRECEDING`: Desde el inicio de la partición
- `N PRECEDING`: N filas antes de la actual
- `CURRENT ROW`: Fila actual
- `N FOLLOWING`: N filas después de la actual
- `UNBOUNDED FOLLOWING`: Hasta el final de la partición

**Defaults cuando hay ORDER BY:**
- Si solo especificas ORDER BY, el frame es `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`
- Si NO hay ORDER BY, el frame es toda la partición

**ROWS vs RANGE:**
- `ROWS`: Cuenta filas físicas (determinístico)
- `RANGE`: Considera valores duplicados (puede incluir más filas si hay empates en ORDER BY)

**Regla de oro:** Usa `ROWS` cuando quieras控制 exacto de filas. Usa `RANGE` cuando los empates deban tratarse igual.

## 3. Mentalidad de Data Engineer

### Cómo piensa un profesional con Window Functions

**1. Evita self-joins innecesarios**

Junior: "Necesito comparar cada fila con la anterior, haré un self-join con ROW_NUMBER()"

Staff: "Usa LAG(), es 10x más performante y legible"

**2. Piensa en particiones, no en loops**

Junior: "Voy a hacer un cursor para calcular el acumulado por cliente"

Staff: "SUM() OVER (PARTITION BY customer_id ORDER BY order_date) resuelve esto en una línea"

**3. Window functions son determinísticas**

Si tu consulta tiene ORDER BY inconsistente, los rankings serán impredecibles. Siempre especifica ORDER BY explícito en funciones de ranking.

**4. El orden de evaluación importa**

Las window functions se evalúan DESPUÉS del WHERE y GROUP BY, pero ANTES del ORDER BY final. Esto significa:
- Puedes usar window functions en el SELECT
- NO puedes usarlas en WHERE (usa un subquery o CTE)
- SÍ puedes usarlas en ORDER BY

**5. Performance: las window functions son O(n log n)**

Cada window function con ORDER BY requiere un sort. Si tienes múltiples window functions con diferentes PARTITION BY u ORDER BY, PostgreSQL hará múltiples sorts.

**Optimización:** Agrupa window functions con la misma partición y orden. PostgreSQL las ejecutará en un solo pass.

```sql
-- MAL: 2 sorts diferentes
SELECT 
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC),
    RANK() OVER (PARTITION BY dept ORDER BY hire_date)
FROM employees;

-- BIEN: 1 solo sort
SELECT 
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC),
    RANK() OVER (PARTITION BY dept ORDER BY salary DESC)
FROM employees;
```

## 4. Ejemplos Prácticos

### Ejemplo 1: Ranking de productos por categoría con revenue

```sql
-- Objetivo: Top 3 productos por revenue dentro de cada categoría
SELECT 
    category_name,
    product_name,
    sku,
    product_revenue,
    category_revenue,
    pct_of_category
FROM (
    SELECT 
        c.name AS category_name,
        p.name AS product_name,
        p.sku,
        SUM(oi.quantity * oi.unit_price - oi.discount_amount) AS product_revenue,
        SUM(SUM(oi.quantity * oi.unit_price - oi.discount_amount)) 
            OVER (PARTITION BY c.id) AS category_revenue,
        ROUND(
            SUM(oi.quantity * oi.unit_price - oi.discount_amount) * 100.0 
            / SUM(SUM(oi.quantity * oi.unit_price - oi.discount_amount)) 
                OVER (PARTITION BY c.id), 
            2
        ) AS pct_of_category,
        ROW_NUMBER() OVER (
            PARTITION BY c.id 
            ORDER BY SUM(oi.quantity * oi.unit_price - oi.discount_amount) DESC
        ) AS rn
    FROM inventory.products p
    JOIN marketing.categories c ON c.id = p.category_id
    JOIN sales.order_items oi ON oi.product_id = p.id
    JOIN sales.orders o ON o.id = oi.order_id
    WHERE o.status <> 'Cancelled'
        AND p.is_active = TRUE
    GROUP BY c.id, c.name, p.id, p.name, p.sku
) ranked
WHERE rn <= 3
ORDER BY category_name, product_revenue DESC;
```

**Análisis:**
- Window function anidada: `SUM(...) OVER (PARTITION BY c.id)` calcula el total de la categoría
- `ROW_NUMBER()` rankea productos dentro de cada categoría
- El subquery permite filtrar por `rn <= 3` (no puedes usar window functions en WHERE directamente)

### Ejemplo 2: Análisis de retención de clientes con LAG

```sql
-- Objetivo: Para cada cliente, mostrar días entre compras consecutivas
WITH customer_orders AS (
    SELECT 
        c.id AS customer_id,
        c.first_name || ' ' || c.last_name AS full_name,
        o.order_date,
        o.net_amount,
        LAG(o.order_date) OVER (PARTITION BY c.id ORDER BY o.order_date) AS prev_order_date,
        LAG(o.net_amount) OVER (PARTITION BY c.id ORDER BY o.order_date) AS prev_order_amount
    FROM core.customers c
    JOIN sales.orders o ON o.customer_id = c.id
    WHERE o.status <> 'Cancelled'
)
SELECT 
    customer_id,
    full_name,
    order_date,
    net_amount,
    prev_order_date,
    (order_date::DATE - prev_order_date::DATE) AS days_between_orders,
    CASE 
        WHEN prev_order_date IS NULL THEN 'First Purchase'
        WHEN (order_date::DATE - prev_order_date::DATE) <= 30 THEN 'Loyal'
        WHEN (order_date::DATE - prev_order_date::DATE) <= 90 THEN 'Active'
        ELSE 'At Risk'
    END AS customer_status
FROM customer_orders
ORDER BY customer_id, order_date;
```

**Análisis:**
- `LAG()` accede a la fila anterior sin self-join
- Cálculo de días entre fechas con resta directa
- CASE para clasificar comportamiento del cliente

### Ejemplo 3: Promedio móvil de 7 días para detección de anomalías

```sql
-- Objetivo: Revenue diario con promedio móvil de 7 días para detectar picos
WITH daily_revenue AS (
    SELECT 
        order_date::DATE AS order_day,
        SUM(net_amount) AS daily_total,
        COUNT(DISTINCT id) AS order_count
    FROM sales.orders
    WHERE status <> 'Cancelled'
        AND order_date >= '2025-01-01'
    GROUP BY order_date::DATE
)
SELECT 
    order_day,
    daily_total,
    order_count,
    ROUND(AVG(daily_total) OVER (
        ORDER BY order_day 
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ), 2) AS moving_avg_7d,
    ROUND(
        (daily_total - AVG(daily_total) OVER (
            ORDER BY order_day 
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        )) * 100.0 
        / AVG(daily_total) OVER (
            ORDER BY order_day 
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ), 
        2
    ) AS pct_from_avg,
    CASE 
        WHEN daily_total > AVG(daily_total) OVER (
            ORDER BY order_day 
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) * 1.5 THEN 'ANOMALY HIGH'
        WHEN daily_total < AVG(daily_total) OVER (
            ORDER BY order_day 
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) * 0.5 THEN 'ANOMALY LOW'
        ELSE 'Normal'
    END AS anomaly_flag
FROM daily_revenue
ORDER BY order_day;
```

**Análisis:**
- `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW`: Ventana de 7 días (hoy + 6 días atrás)
- Promedio móvil para suavizar volatilidad
- Detección de anomalías comparando vs promedio móvil

## 5. Code Review: Consulta de Junior vs Profesional

### Consulta Junior

```sql
-- "Necesito el top 1 producto por categoría"
SELECT 
    c.name AS category_name,
    p.name AS product_name,
    SUM(oi.quantity) AS total_sold
FROM marketing.categories c
JOIN inventory.products p ON p.category_id = c.id
JOIN sales.order_items oi ON oi.product_id = p.id
JOIN sales.orders o ON o.id = oi.order_id
WHERE o.status <> 'Cancelled'
GROUP BY c.id, c.name, p.id, p.name
ORDER BY c.name, total_sold DESC;
```

### Análisis del Junior

**Problemas:**
1. **No filtra top 1:** Solo ordena, pero muestra TODOS los productos
2. **Usa ORDER BY en lugar de ranking:** No hay forma de filtrar "el primero"
3. **Falta contexto:** No muestra el total de la categoría ni el porcentaje

**Resultado:** Devuelve cientos de filas cuando debería devolver 1 por categoría.

### Versión Profesional

```sql
WITH product_sales AS (
    SELECT 
        c.id AS category_id,
        c.name AS category_name,
        p.id AS product_id,
        p.name AS product_name,
        SUM(oi.quantity) AS total_sold,
        SUM(SUM(oi.quantity)) OVER (PARTITION BY c.id) AS category_total,
        ROW_NUMBER() OVER (PARTITION BY c.id ORDER BY SUM(oi.quantity) DESC) AS rn
    FROM marketing.categories c
    JOIN inventory.products p ON p.category_id = c.id
    JOIN sales.order_items oi ON oi.product_id = p.id
    JOIN sales.orders o ON o.id = oi.order_id
    WHERE o.status <> 'Cancelled'
    GROUP BY c.id, c.name, p.id, p.name
)
SELECT 
    category_name,
    product_name,
    total_sold,
    category_total,
    ROUND(total_sold * 100.0 / category_total, 2) AS pct_of_category
FROM product_sales
WHERE rn = 1
ORDER BY category_name;
```

**Mejoras:**
1. **CTE para claridad:** Separa lógica de ranking del resultado final
2. **ROW_NUMBER() para top-N:** Permite filtrar exactamente el #1
3. **Window function anidada:** Calcula total de categoría sin subquery
4. **Porcentaje de contribución:** Da contexto de negocio
5. **Performance:** Un solo pass de datos, sin self-joins

## 6. Errores Frecuentes

### Error 1: Usar window functions en WHERE

```sql
-- MAL: Error de sintaxis
SELECT *
FROM sales.orders
WHERE ROW_NUMBER() OVER (ORDER BY order_date) <= 10;

-- BIEN: Usa subquery o CTE
WITH ranked AS (
    SELECT *, ROW_NUMBER() OVER (ORDER BY order_date) AS rn
    FROM sales.orders
)
SELECT * FROM ranked WHERE rn <= 10;
```

### Error 2: Olvidar ORDER BY en funciones de ranking

```sql
-- MAL: ROW_NUMBER sin ORDER BY es no determinístico
SELECT ROW_NUMBER() OVER (PARTITION BY department_id) AS rn
FROM hr.employees;

-- BIEN: Siempre especifica ORDER BY
SELECT ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY hire_date) AS rn
FROM hr.employees;
```

### Error 3: Confundir ROWS con RANGE

```sql
-- Si tienes empates en ORDER BY:
-- ROWS BETWEEN 1 PRECEDING AND CURRENT ROW: Cuenta 2 filas físicas
-- RANGE BETWEEN 1 PRECEDING AND CURRENT ROW: Incluye todas las filas con valores "cercanos"

-- Ejemplo con salaries duplicados:
SELECT 
    salary,
    COUNT(*) OVER (ORDER BY salary ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS row_count,
    COUNT(*) OVER (ORDER BY salary RANGE BETWEEN 1 PRECEDING AND CURRENT ROW) AS range_count
FROM hr.employees;
```

### Error 4: No entender el default frame

```sql
-- Cuando hay ORDER BY, el default es:
-- RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

-- Esto significa que SUM() OVER (ORDER BY date) es un acumulado, no la suma total
SELECT 
    order_date,
    SUM(net_amount) OVER (ORDER BY order_date) AS running_total,  -- Acumulado
    SUM(net_amount) OVER () AS grand_total  -- Sin ORDER BY = toda la tabla
FROM sales.orders;
```

### Error 5: Múltiples window functions con diferentes particiones

```sql
-- MAL: 2 sorts diferentes, performance pobre
SELECT 
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary) AS rn_salary,
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY hire_date) AS rn_seniority
FROM hr.employees;

-- BIEN: Si es posible, usa la misma partición y orden
-- O acepta el costo de múltiples sorts si es necesario para el negocio
```

## 7. Resumen

### Conceptos Clave

1. **Window functions no colapsan filas:** Cada fila mantiene su identidad
2. **PARTITION BY:** Divide en particiones independientes (como mini GROUP BY)
3. **ORDER BY:** Define orden dentro de partición (crítico para rankings)
4. **Frame clause:** Controla qué filas se incluyen en el cálculo
5. **3 categorías:** Ranking, Offset (LAG/LEAD), Agregación como window

### Cuándo Usar Cada Función

| Función | Caso de Uso |
|---------|-------------|
| `ROW_NUMBER()` | Top-N sin empates, IDs únicos |
| `RANK()` | Rankings con empates que dejan huecos |
| `DENSE_RANK()` | Rankings con empates sin huecos |
| `LAG()/LEAD()` | Comparar filas adyacentes, series temporales |
| `SUM() OVER()` | Running totals, acumulados |
| `AVG() OVER()` | Promedios móviles, comparativas |
| `FIRST_VALUE()/LAST_VALUE()` | Primer/último valor en ventana |
| `NTILE()` | Cuartiles, deciles, percentiles |

### Reglas de Oro

1. **No puedes usar window functions en WHERE:** Usa subquery o CTE
2. **Siempre especifica ORDER BY en rankings:** Evita resultados no determinísticos
3. **Usa ROWS para control exacto:** A menos que necesites tratar empates igual
4. **Agrupa window functions con misma partición:** Mejora performance
5. **Piensa en particiones, no en loops:** Window functions reemplazan cursores
