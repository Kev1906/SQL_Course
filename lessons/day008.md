# Día 8: Date Functions - Dominando el Tiempo en SQL

## 1. Objetivo del Día

Dominar las funciones de fecha y hora en PostgreSQL para manipular, extraer, comparar y transformar datos temporales. Al final de este día, sabrás manejar zonas horarias, intervalos, truncamiento, extracción de componentes, y cálculos de diferencia entre fechas como un Staff Engineer en producción.

## 2. Teoría: Date Functions como Staff Engineer

### ¿Por qué las fechas son críticas en Data Engineering?

Las fechas son el tipo de dato más común en sistemas transaccionales y analytics. Cada orden, evento, log, transacción, tiene un timestamp. Un Data Engineer que no domina las funciones de fecha es como un cirujano que no sabe usar el bisturí.

**Problemas comunes en producción:**
- Zonas horarias mal manejadas → reportes con datos del día equivocado
- Comparaciones de timestamps sin truncar → joins que no matchean
- Cálculos de antigüedad incorrectos → métricas de retención erróneas
- Extracción de períodos mal hecha → dashboards con datos inconsistentes

### Tipos de Datos Temporales en PostgreSQL

| Tipo | Almacena | Ejemplo |
|------|----------|---------|
| `DATE` | Solo fecha (año, mes, día) | `2025-03-15` |
| `TIME` | Solo hora (sin fecha) | `14:30:45` |
| `TIMESTAMP` | Fecha + hora (sin zona horaria) | `2025-03-15 14:30:45` |
| `TIMESTAMPTZ` | Fecha + hora + zona horaria | `2025-03-15 14:30:45-05` |
| `INTERVAL` | Duración (días, horas, etc.) | `2 days 3 hours` |

**Regla del Staff Engineer:** Siempre usa `TIMESTAMPTZ` en producción. Nunca `TIMESTAMP` sin zona horaria. Las fechas sin zona horaria causan bugs cuando tu aplicación corre en múltiples regiones.

### Funciones de Extracción

#### `EXTRACT(field FROM timestamp)`

Extrae un componente específico de una fecha/hora.

```sql
SELECT 
    order_date,
    EXTRACT(YEAR FROM order_date) AS year,
    EXTRACT(MONTH FROM order_date) AS month,
    EXTRACT(DAY FROM order_date) AS day,
    EXTRACT(DOW FROM order_date) AS day_of_week,  -- 0=Sunday, 6=Saturday
    EXTRACT(DOY FROM order_date) AS day_of_year,
    EXTRACT(HOUR FROM order_date) AS hour,
    EXTRACT(QUARTER FROM order_date) AS quarter
FROM sales.orders
LIMIT 5;
```

**Campos más usados:**
- `YEAR`, `MONTH`, `DAY`: componentes básicos
- `DOW`: día de la semana (0=Domingo, 6=Sábado)
- `DOY`: día del año (1-366)
- `QUARTER`: trimestre (1-4)
- `WEEK`: número de semana del año
- `HOUR`, `MINUTE`, `SECOND`: componentes de hora
- `EPOCH`: segundos desde 1970-01-01 00:00:00 UTC

#### `DATE_PART(field, timestamp)`

Alternativa a `EXTRACT`, misma funcionalidad.

```sql
SELECT 
    order_date,
    DATE_PART('year', order_date) AS year,
    DATE_PART('month', order_date) AS month
FROM sales.orders;
```

**Staff Engineer dice:** Usa `EXTRACT` por legibilidad. `DATE_PART` es legacy.

### Funciones de Truncamiento

#### `DATE_TRUNC(field, timestamp)`

Trunca una fecha al nivel especificado, "redondeando hacia abajo".

```sql
SELECT 
    order_date,
    DATE_TRUNC('year', order_date) AS year_start,
    DATE_TRUNC('month', order_date) AS month_start,
    DATE_TRUNC('day', order_date) AS day_start,
    DATE_TRUNC('hour', order_date) AS hour_start
FROM sales.orders;
```

**Casos de uso críticos:**
1. **Agrupar por día:** `DATE_TRUNC('day', order_date)` agrupa todos los eventos del mismo día
2. **Reportes mensuales:** `DATE_TRUNC('month', order_date)` para consolidar por mes
3. **Comparar fechas sin hora:** `DATE_TRUNC('day', timestamp1) = DATE_TRUNC('day', timestamp2)`

```sql
-- Agrupar ventas por mes
SELECT 
    DATE_TRUNC('month', order_date) AS month,
    COUNT(*) AS order_count,
    SUM(net_amount) AS total_revenue
FROM sales.orders
WHERE status <> 'Cancelled'
GROUP BY DATE_TRUNC('month', order_date)
ORDER BY month;
```

### Funciones de Conversión y Cast

#### Cast de TIMESTAMP a DATE

```sql
SELECT 
    order_date,
    order_date::DATE AS order_date_only,
    CAST(order_date AS DATE) AS order_date_only_v2
FROM sales.orders;
```

**Staff Engineer dice:** Usa `::DATE` por concisión. Es equivalente a `CAST(... AS DATE)`.

#### `TO_CHAR(timestamp, format)` y `TO_DATE(text, format)`

Convierte fechas a texto formateado y viceversa.

```sql
SELECT 
    order_date,
    TO_CHAR(order_date, 'YYYY-MM-DD') AS iso_date,
    TO_CHAR(order_date, 'DD/MM/YYYY') AS european_date,
    TO_CHAR(order_date, 'Month DD, YYYY') AS readable_date,
    TO_CHAR(order_date, 'Day') AS day_name,
    TO_CHAR(order_date, 'HH24:MI:SS') AS time_24h
FROM sales.orders;
```

**Formatos más usados:**
- `YYYY`: año 4 dígitos
- `MM`: mes 2 dígitos
- `DD`: día 2 dígitos
- `HH24`: hora 24h
- `MI`: minutos
- `SS`: segundos
- `Day`: nombre del día (Monday, Tuesday, etc.)
- `Month`: nombre del mes (January, February, etc.)

### Funciones de Fecha Actual

```sql
SELECT 
    CURRENT_DATE,           -- Fecha actual (DATE)
    CURRENT_TIME,           -- Hora actual (TIME con zona horaria)
    CURRENT_TIMESTAMP,      -- Fecha+hora actual (TIMESTAMPTZ)
    NOW(),                  -- Alias de CURRENT_TIMESTAMP
    LOCALTIME,              -- Hora local (sin zona horaria)
    LOCALTIMESTAMP;         -- Fecha+hora local (sin zona horaria)
```

**Regla del Staff Engineer:** Usa `CURRENT_TIMESTAMP` o `NOW()` en producción. Nunca `LOCALTIMESTAMP` porque no tiene zona horaria y causa bugs en sistemas distribuidos.

### Aritmética de Fechas e INTERVAL

PostgreSQL permite sumar/restar intervalos directamente.

```sql
SELECT 
    order_date,
    order_date + INTERVAL '7 days' AS one_week_later,
    order_date - INTERVAL '1 month' AS one_month_before,
    order_date + INTERVAL '2 hours 30 minutes' AS later_same_day,
    order_date + INTERVAL '1 year' AS next_year
FROM sales.orders;
```

**Diferencia entre fechas:**

```sql
SELECT 
    order_date,
    delivered_at,
    delivered_at - order_date AS delivery_duration,  -- Devuelve INTERVAL
    EXTRACT(DAY FROM delivered_at - order_date) AS days_to_deliver,
    EXTRACT(HOUR FROM delivered_at - order_date) AS hours_to_deliver
FROM sales.orders
WHERE delivered_at IS NOT NULL;
```

**Edad/antigüedad:**

```sql
SELECT 
    first_name,
    last_name,
    hire_date,
    AGE(CURRENT_DATE, hire_date) AS tenure,  -- Devuelve INTERVAL (years, months, days)
    EXTRACT(YEAR FROM AGE(CURRENT_DATE, hire_date)) AS years_tenure,
    CURRENT_DATE - hire_date AS days_employed  -- Devuelve INTEGER (días)
FROM hr.employees;
```

### Funciones de Manipulación Avanzada

#### `DATE_BIN(stride, timestamp, origin)` (PostgreSQL 14+)

Binnea timestamps en intervalos regulares. Útil para time-series.

```sql
-- Agrupar eventos en buckets de 15 minutos
SELECT 
    DATE_BIN('15 minutes', created_at, TIMESTAMP '2025-01-01') AS time_bucket,
    COUNT(*) AS event_count
FROM audit.logs
GROUP BY time_bucket
ORDER BY time_bucket;
```

#### `MAKE_DATE(year, month, day)` y `MAKE_TIMESTAMP(...)`

Construye fechas desde componentes.

```sql
SELECT 
    MAKE_DATE(2025, 3, 15) AS custom_date,
    MAKE_TIMESTAMP(2025, 3, 15, 14, 30, 0) AS custom_timestamp;
```

### Zonas Horarias: El Infierno de los Data Engineers

PostgreSQL almacena `TIMESTAMPTZ` en UTC internamente. Cuando consultas, convierte a la zona horaria de la sesión.

```sql
-- Ver zona horaria actual de la sesión
SHOW timezone;

-- Cambiar zona horaria de la sesión
SET timezone = 'America/New_York';
SET timezone = 'UTC';

-- Convertir timestamp a otra zona horaria
SELECT 
    order_date,
    order_date AT TIME ZONE 'UTC' AS utc_time,
    order_date AT TIME ZONE 'America/New_York' AS ny_time,
    order_date AT TIME ZONE 'Europe/London' AS london_time
FROM sales.orders;
```

**Problema clásico:** Tu servidor corre en UTC, pero tu negocio está en México. Si filtras `WHERE order_date::DATE = '2025-03-15'`, puedes estar incluyendo órdenes del 14 de marzo a las 23:00 hora local.

**Solución profesional:**

```sql
-- Convertir a zona horaria local ANTES de truncar
SELECT 
    order_date AT TIME ZONE 'America/Mexico_City' AS local_time,
    (order_date AT TIME ZONE 'America/Mexico_City')::DATE AS local_date
FROM sales.orders;
```

## 3. Mentalidad de Data Engineer

### Cómo piensa un profesional con fechas

**1. Siempre piensa en zonas horarias**

Junior: "Voy a usar `order_date::DATE` para agrupar por día"

Staff: "¿En qué zona horaria está el negocio? Si el servidor está en UTC y el negocio en LATAM, `::DATE` puede agrupar mal. Necesito convertir a zona horaria local primero."

**2. Truncar antes de comparar**

Junior: `WHERE order_date = '2025-03-15'`

Staff: "Si `order_date` es `TIMESTAMPTZ`, esta comparación falla porque '2025-03-15' se interpreta como medianoche UTC. Debo usar `WHERE order_date::DATE = '2025-03-15'` o `WHERE DATE_TRUNC('day', order_date AT TIME ZONE 'America/Mexico_City') = '2025-03-15'`."

**3. INTERVAL > cálculos manuales**

Junior: `WHERE order_date > CURRENT_TIMESTAMP - 86400 * INTERVAL '1 second'` (7 días en segundos)

Staff: `WHERE order_date > CURRENT_TIMESTAMP - INTERVAL '7 days'`

**4. Cuidado con AGE() vs resta directa**

- `AGE(date1, date2)` devuelve INTERVAL con años, meses, días (pero meses y días son imprecisos)
- `date1 - date2` devuelve INTEGER (días exactos) o INTERVAL (si son timestamps)

```sql
-- AGE: "2 years 3 mons 15 days" (impreciso para cálculos)
SELECT AGE('2025-03-15', '2023-01-01');

-- Resta directa: 804 días (exacto)
SELECT '2025-03-15'::DATE - '2023-01-01'::DATE;
```

**5. DATE_TRUNC es tu mejor amigo para agregaciones**

Siempre que agrupes por período, usa `DATE_TRUNC`:

```sql
-- MAL: Agrupa por timestamp exacto (cada fila es su propio grupo)
SELECT order_date, COUNT(*) FROM sales.orders GROUP BY order_date;

-- BIEN: Agrupa por día
SELECT DATE_TRUNC('day', order_date) AS day, COUNT(*) 
FROM sales.orders 
GROUP BY day;
```

**6. Evita funciones en columnas indexadas**

Si `order_date` tiene índice, `WHERE DATE_TRUNC('month', order_date) = '2025-03-01'` NO usa el índice.

**Solución:** Usa rangos:

```sql
-- MAL: No usa índice
WHERE DATE_TRUNC('month', order_date) = '2025-03-01'

-- BIEN: Usa índice (range scan)
WHERE order_date >= '2025-03-01' AND order_date < '2025-04-01'
```

## 4. Ejemplos Prácticos

### Ejemplo 1: Análisis de estacionalidad - ventas por día de la semana y hora

```sql
-- Objetivo: Entender patrones de compra por día de la semana y franja horaria
-- para optimizar campañas de marketing y staffing de soporte

SELECT 
    CASE EXTRACT(DOW FROM order_date AT TIME ZONE 'America/Mexico_City')
        WHEN 0 THEN 'Domingo'
        WHEN 1 THEN 'Lunes'
        WHEN 2 THEN 'Martes'
        WHEN 3 THEN 'Miércoles'
        WHEN 4 THEN 'Jueves'
        WHEN 5 THEN 'Viernes'
        WHEN 6 THEN 'Sábado'
    END AS day_of_week,
    CASE 
        WHEN EXTRACT(HOUR FROM order_date AT TIME ZONE 'America/Mexico_City') BETWEEN 6 AND 11 THEN 'Mañana (6-11)'
        WHEN EXTRACT(HOUR FROM order_date AT TIME ZONE 'America/Mexico_City') BETWEEN 12 AND 17 THEN 'Tarde (12-17)'
        WHEN EXTRACT(HOUR FROM order_date AT TIME ZONE 'America/Mexico_City') BETWEEN 18 AND 23 THEN 'Noche (18-23)'
        ELSE 'Madrugada (0-5)'
    END AS time_slot,
    COUNT(*) AS order_count,
    SUM(net_amount) AS total_revenue,
    ROUND(AVG(net_amount), 2) AS avg_ticket,
    ROUND(SUM(net_amount) / COUNT(*), 2) AS revenue_per_order
FROM sales.orders
WHERE status <> 'Cancelled'
    AND order_date >= CURRENT_DATE - INTERVAL '1 year'
GROUP BY 
    EXTRACT(DOW FROM order_date AT TIME ZONE 'America/Mexico_City'),
    CASE 
        WHEN EXTRACT(HOUR FROM order_date AT TIME ZONE 'America/Mexico_City') BETWEEN 6 AND 11 THEN 'Mañana (6-11)'
        WHEN EXTRACT(HOUR FROM order_date AT TIME ZONE 'America/Mexico_City') BETWEEN 12 AND 17 THEN 'Tarde (12-17)'
        WHEN EXTRACT(HOUR FROM order_date AT TIME ZONE 'America/Mexico_City') BETWEEN 18 AND 23 THEN 'Noche (18-23)'
        ELSE 'Madrugada (0-5)'
    END
ORDER BY 
    EXTRACT(DOW FROM order_date AT TIME ZONE 'America/Mexico_City'),
    time_slot;
```

**Análisis:**
- Convierte UTC a zona horaria local antes de extraer componentes
- Usa `EXTRACT(DOW ...)` para día de la semana
- Agrupa horas en franjas de negocio (mañana, tarde, noche, madrugada)
- Filtra último año para análisis reciente
- Métricas: volumen, revenue, ticket promedio

### Ejemplo 2: Cohortes de retención mensual - análisis de cohortes clásico

```sql
-- Objetivo: Calcular retención de clientes por cohorte mensual
-- (clientes adquiridos en mes X, ¿qué % volvió a comprar en mes X+1, X+2, etc.?)

WITH customer_cohorts AS (
    -- Asignar cada cliente a su cohorte (mes de primera compra)
    SELECT 
        customer_id,
        DATE_TRUNC('month', MIN(order_date)) AS cohort_month
    FROM sales.orders
    WHERE status <> 'Cancelled'
    GROUP BY customer_id
),
customer_activity AS (
    -- Para cada cliente, listar todos los meses en que compró
    SELECT 
        o.customer_id,
        cc.cohort_month,
        DATE_TRUNC('month', o.order_date) AS activity_month,
        EXTRACT(YEAR FROM AGE(
            DATE_TRUNC('month', o.order_date), 
            cc.cohort_month
        )) * 12 + EXTRACT(MONTH FROM AGE(
            DATE_TRUNC('month', o.order_date), 
            cc.cohort_month
        )) AS months_since_cohort
    FROM sales.orders o
    JOIN customer_cohorts cc ON cc.customer_id = o.customer_id
    WHERE o.status <> 'Cancelled'
    GROUP BY o.customer_id, cc.cohort_month, DATE_TRUNC('month', o.order_date)
),
cohort_size AS (
    -- Tamaño de cada cohorte
    SELECT 
        cohort_month,
        COUNT(DISTINCT customer_id) AS cohort_size
    FROM customer_cohorts
    GROUP BY cohort_month
)
SELECT 
    TO_CHAR(ca.cohort_month, 'YYYY-MM') AS cohort,
    cs.cohort_size,
    ca.months_since_cohort,
    COUNT(DISTINCT ca.customer_id) AS active_customers,
    ROUND(
        COUNT(DISTINCT ca.customer_id) * 100.0 / cs.cohort_size, 
        2
    ) AS retention_pct
FROM customer_activity ca
JOIN cohort_size cs ON cs.cohort_month = ca.cohort_month
WHERE ca.months_since_cohort <= 12  -- Analizar primeros 12 meses
GROUP BY ca.cohort_month, cs.cohort_size, ca.months_since_cohort
ORDER BY ca.cohort_month, ca.months_since_cohort;
```

**Análisis:**
- CTE `customer_cohorts`: asigna cada cliente a su cohorte (mes de primera compra)
- CTE `customer_activity`: calcula meses transcurridos desde cohorte
- `AGE()` + `EXTRACT(MONTH FROM ...)` para calcular diferencia en meses
- Métrica de retención: % de clientes activos en cada mes post-adquisición
- Análisis clásico de producto: ¿qué tan bien retenemos clientes?

### Ejemplo 3: SLA de entrega - análisis de cumplimiento de promesas logísticas

```sql
-- Objetivo: Calcular % de órdenes entregadas dentro del SLA prometido
-- y detectar patrones de incumplimiento por región, transportista, etc.

SELECT 
    DATE_TRUNC('month', o.order_date) AS order_month,
    s.name AS shipping_method,
    COUNT(*) AS total_orders,
    COUNT(*) FILTER (
        WHERE o.delivered_at IS NOT NULL 
          AND o.delivered_at <= o.order_date + (s.estimated_days || ' days')::INTERVAL
    ) AS on_time_deliveries,
    ROUND(
        COUNT(*) FILTER (
            WHERE o.delivered_at IS NOT NULL 
              AND o.delivered_at <= o.order_date + (s.estimated_days || ' days')::INTERVAL
        ) * 100.0 / NULLIF(COUNT(*) FILTER (WHERE o.delivered_at IS NOT NULL), 0),
        2
    ) AS on_time_pct,
    ROUND(AVG(
        EXTRACT(DAY FROM o.delivered_at - o.order_date)
    ) FILTER (WHERE o.delivered_at IS NOT NULL), 2) AS avg_delivery_days,
    ROUND(AVG(
        EXTRACT(DAY FROM o.delivered_at - o.order_date) 
        - s.estimated_days
    ) FILTER (
        WHERE o.delivered_at IS NOT NULL 
          AND o.delivered_at > o.order_date + (s.estimated_days || ' days')::INTERVAL
    ), 2) AS avg_days_late
FROM sales.orders o
JOIN logistics.shipping_methods s ON s.id = o.shipping_method_id
WHERE o.status <> 'Cancelled'
    AND o.order_date >= CURRENT_DATE - INTERVAL '6 months'
GROUP BY DATE_TRUNC('month', o.order_date), s.name
ORDER BY order_month DESC, s.name;
```

**Análisis:**
- `estimated_days || ' days'::INTERVAL`: construye intervalo dinámico desde columna
- `FILTER (WHERE ...)`: agrega condicionalmente (más limpio que CASE + SUM)
- Compara `delivered_at` vs `order_date + SLA` para determinar puntualidad
- Métricas: % on-time, días promedio de entrega, días promedio de retraso
- Agrupa por mes y método de envío para detectar tendencias

## 5. Code Review: Consulta de Junior vs Profesional

### Consulta Junior

```sql
-- "Necesito las ventas de los últimos 30 días agrupadas por día"
SELECT 
    order_date,
    SUM(net_amount) AS total
FROM sales.orders
WHERE order_date > NOW() - 30
GROUP BY order_date
ORDER BY order_date;
```

### Análisis del Junior

**Problemas:**
1. **`NOW() - 30`:** Esto resta 30 segundos, no 30 días. Debe ser `NOW() - INTERVAL '30 days'`.
2. **`GROUP BY order_date`:** Si `order_date` es `TIMESTAMPTZ`, cada timestamp es único. Debe truncar a día.
3. **Sin zona horaria:** Si el servidor está en UTC y el negocio en LATAM, agrupa mal.
4. **Sin filtro de status:** Incluye órdenes canceladas.
5. **Sin contexto:** No muestra cantidad de órdenes, ticket promedio, ni comparación con período anterior.

### Versión Profesional

```sql
WITH daily_sales AS (
    SELECT 
        (order_date AT TIME ZONE 'America/Mexico_City')::DATE AS sale_date,
        COUNT(*) AS order_count,
        SUM(net_amount) AS total_revenue,
        ROUND(AVG(net_amount), 2) AS avg_ticket
    FROM sales.orders
    WHERE status <> 'Cancelled'
        AND order_date >= (CURRENT_DATE AT TIME ZONE 'America/Mexico_City') - INTERVAL '30 days'
    GROUP BY (order_date AT TIME ZONE 'America/Mexico_City')::DATE
)
SELECT 
    sale_date,
    TO_CHAR(sale_date, 'Day') AS day_name,
    order_count,
    total_revenue,
    avg_ticket,
    LAG(total_revenue) OVER (ORDER BY sale_date) AS prev_day_revenue,
    ROUND(
        (total_revenue - LAG(total_revenue) OVER (ORDER BY sale_date)) * 100.0 
        / NULLIF(LAG(total_revenue) OVER (ORDER BY sale_date), 0),
        2
    ) AS revenue_change_pct
FROM daily_sales
ORDER BY sale_date DESC;
```

**Mejoras:**
1. **Conversión de zona horaria:** Convierte a hora local antes de truncar
2. **`INTERVAL '30 days'`:** Sintaxis correcta para restar días
3. **Truncamiento a día:** `(order_date AT TIME ZONE '...')::DATE` agrupa correctamente
4. **Filtro de status:** Excluye canceladas
5. **Window function:** Compara cada día con el anterior (análisis de tendencia)
6. **Contexto de negocio:** Muestra día de la semana, ticket promedio, cambio vs día anterior

## 6. Errores Frecuentes

### Error 1: Restar números en lugar de INTERVAL

```sql
-- MAL: Resta 30 segundos, no 30 días
WHERE order_date > NOW() - 30

-- BIEN: Usa INTERVAL
WHERE order_date > NOW() - INTERVAL '30 days'
```

### Error 2: Comparar TIMESTAMP con DATE sin truncar

```sql
-- MAL: Compara timestamp exacto con fecha (solo matchea medianoche)
WHERE order_date = '2025-03-15'

-- BIEN: Truncar a día
WHERE order_date::DATE = '2025-03-15'

-- MEJOR: Rango (usa índice)
WHERE order_date >= '2025-03-15' AND order_date < '2025-03-16'
```

### Error 3: Ignorar zonas horarias en sistemas multi-región

```sql
-- MAL: Asume que order_date está en zona horaria local
SELECT order_date::DATE, COUNT(*) 
FROM sales.orders 
GROUP BY order_date::DATE;

-- BIEN: Convierte a zona horaria local primero
SELECT (order_date AT TIME ZONE 'America/Mexico_City')::DATE AS local_date, COUNT(*)
FROM sales.orders
GROUP BY local_date;
```

### Error 4: Usar AGE() para cálculos exactos

```sql
-- MAL: AGE devuelve "2 years 3 mons 15 days" (impreciso)
SELECT AGE('2025-03-15', '2023-01-01');

-- BIEN: Resta directa para días exactos
SELECT '2025-03-15'::DATE - '2023-01-01'::DATE AS days_diff;

-- BIEN: EXTRACT para componentes específicos
SELECT 
    EXTRACT(YEAR FROM AGE('2025-03-15', '2023-01-01')) AS years,
    EXTRACT(MONTH FROM AGE('2025-03-15', '2023-01-01')) AS months;
```

### Error 5: DATE_TRUNC en WHERE sin considerar índices

```sql
-- MAL: No usa índice en order_date
WHERE DATE_TRUNC('month', order_date) = '2025-03-01'

-- BIEN: Rango que usa índice
WHERE order_date >= '2025-03-01' AND order_date < '2025-04-01'
```

### Error 6: Confundir DOW (día de la semana) con números humanos

```sql
-- MAL: Asume que 1=Lunes (en PostgreSQL, 0=Domingo, 1=Lunes, ..., 6=Sábado)
WHERE EXTRACT(DOW FROM order_date) = 1  -- Esto es Lunes, pero confunde a juniors

-- BIEN: Documentar o usar CASE para claridad
WHERE EXTRACT(DOW FROM order_date) = 1  -- 1 = Lunes
-- O mejor:
WHERE TO_CHAR(order_date, 'Day') = 'Monday'
```

## 7. Resumen

### Conceptos Clave

1. **TIMESTAMPTZ > TIMESTAMP:** Siempre usa timestamps con zona horaria en producción
2. **EXTRACT vs DATE_PART:** `EXTRACT` es más legible, `DATE_PART` es legacy
3. **DATE_TRUNC:** Trunca fechas para agrupar por período (día, mes, año)
4. **INTERVAL:** Usa intervalos para aritmética de fechas, no números
5. **Zonas horarias:** Convierte a zona horaria local ANTES de truncar o filtrar
6. **AGE() vs resta:** `AGE()` devuelve INTERVAL impreciso, resta directa da días exactos

### Funciones Más Usadas

| Función | Uso |
|---------|-----|
| `EXTRACT(field FROM ts)` | Extraer componente (año, mes, día, hora) |
| `DATE_TRUNC(field, ts)` | Truncar a período (día, mes, año) |
| `ts::DATE` | Convertir timestamp a date |
| `ts + INTERVAL 'n days'` | Sumar/restar días |
| `ts1 - ts2` | Diferencia entre fechas |
| `AGE(ts1, ts2)` | Diferencia como INTERVAL (años, meses, días) |
| `NOW()` / `CURRENT_TIMESTAMP` | Fecha+hora actual |
| `ts AT TIME ZONE 'zone'` | Convertir a zona horaria |

### Reglas de Oro

1. **Siempre usa TIMESTAMPTZ** en schemas de producción
2. **Convierte a zona horaria local** antes de truncar o filtrar por fecha
3. **Usa INTERVAL** para aritmética, nunca números sueltos
4. **Trunca con DATE_TRUNC** antes de agrupar por período
5. **Usa rangos en WHERE** en lugar de DATE_TRUNC para aprovechar índices
6. **Documenta DOW** (0=Domingo, 6=Sábado) para evitar confusión
7. **AGE() es impreciso** para cálculos exactos, usa resta directa
