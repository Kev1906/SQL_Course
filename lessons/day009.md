# Día 9: UPDATE y DELETE - El Día Que Puedes Romper Producción

## 1. Objetivo del Día

Dominar las sentencias DML de modificación y borrado (`UPDATE`, `DELETE`) con el rigor de un Staff Engineer: transacciones, cláusula `RETURNING`, joins en DML, restricciones de integridad, efectos de triggers y patrones de seguridad. Al final de este día, escribirás DML que puede correr en producción sin que nadie tenga que restaurar un backup a las 3 AM.

## 2. Teoría: DML como Staff Engineer

### ¿Por qué este día es diferente a todos los anteriores?

Hasta hoy, todo lo que escribiste era de **solo lectura**. Si tu `SELECT` estaba mal, el peor resultado era un número incorrecto en un reporte. Hoy eso cambia:

- Un `SELECT` malo da datos incorrectos.
- Un `UPDATE` malo **destruye datos correctos**.
- Un `DELETE` malo **elimina datos que quizás no puedas recuperar**.

En Amazon, Stripe o Uber, un junior no tiene permisos de escritura directa en producción. Escribe el DML, lo revisa un senior, corre en staging, se valida, y recién entonces toca producción. Esa disciplina la vas a aprender hoy.

**Los 3 mandamientos del DML profesional:**

1. **Nunca escribas un `UPDATE`/`DELETE` sin haber corrido antes el `SELECT` equivalente** con el mismo `WHERE`. Si el `SELECT` devuelve 500,000 filas y esperabas 50, ya sabes que algo está mal — sin haber roto nada.
2. **Nunca corras DML fuera de una transacción en un entorno que no sea producción automatizada.** `BEGIN` → validar → `COMMIT` o `ROLLBACK`.
3. **Siempre usa `RETURNING`** para ver exactamente qué filas cambiaron.

### Sintaxis de UPDATE

```sql
UPDATE schema.table
SET 
    column1 = value1,
    column2 = expression2
WHERE condition
RETURNING columns;
```

**Reglas no negociables:**

- El `WHERE` define el **blast radius** (radio de explosión). Sin `WHERE`, actualizas **TODA la tabla**. No hay confirmación, no hay "¿estás seguro?". Simplemente pasa.
- PostgreSQL valida **todas** las constraints (`CHECK`, `NOT NULL`, `UNIQUE`, FK, dominios) por cada fila. Si una sola fila viola una constraint, **toda la sentencia falla y se revierte** (atomicidad).
- Cada fila actualizada toma un **row lock** hasta que la transacción termina. Un `UPDATE` de 1M de filas = 1M de locks.

#### UPDATE con expresiones

```sql
-- Aumento del 8% a productos de una categoría
UPDATE inventory.products
SET price = ROUND(price * 1.08, 2)
WHERE category_id = 5;
```

**Ojo con las constraints calculadas.** En `sales.orders` existe:

```sql
CONSTRAINT chk_net_amount CHECK (net_amount = total_amount - discount_amount)
```

Esto significa que **no puedes** actualizar `total_amount` sin actualizar `net_amount` en la misma sentencia:

```sql
-- FALLA: viola chk_net_amount
UPDATE sales.orders
SET total_amount = 1000.00
WHERE id = 12345;

-- CORRECTO: ambas columnas en la misma sentencia
UPDATE sales.orders
SET 
    total_amount = 1000.00,
    net_amount = 1000.00 - discount_amount
WHERE id = 12345;
```

**Staff Engineer dice:** En Postgres, las `CHECK` constraints se evalúan al final de cada fila, viendo los valores **nuevos** de todas las columnas. Por eso actualizar ambas columnas en un solo `UPDATE` funciona. Dos `UPDATE` separados fallarían en el primero.

#### UPDATE con RETURNING

```sql
UPDATE inventory.products
SET price = ROUND(price * 1.08, 2)
WHERE category_id = 5
RETURNING id, sku, name, price AS new_price;
```

`RETURNING` devuelve las filas **ya modificadas**. Es tu evidencia de qué cambió. En producción, guarda esa salida: es tu mini-auditoría.

### UPDATE ... FROM: el UPDATE con JOIN

El error clásico de junior es querer "hacer un UPDATE con un JOIN" usando sintaxis de otros motores. En PostgreSQL se usa `FROM`:

```sql
UPDATE sales.orders o
SET employee_id = e.id
FROM hr.employees e
WHERE e.email = 'supervisor@datamartx.com'
  AND o.employee_id IS NULL
  AND o.status = 'Pending';
```

**TRAMPA MORTAL — el cross join accidental:**

```sql
-- PELIGRO: esto NO hace lo que crees
UPDATE sales.orders o
SET employee_id = e.id
FROM hr.employees e
WHERE o.employee_id IS NULL;
-- No hay condición que una 'o' con 'e' → CROSS JOIN
-- Cada orden se actualiza con un empleado ARBITRARIO
```

Si el `FROM` no tiene una condición que conecte la tabla objetivo con la tabla fuente, PostgreSQL hace un **cross join implícito** y cada fila se actualiza con valores impredecibles. El `UPDATE` "funciona" sin error. Es el peor tipo de bug: silencioso.

**Regla de oro:** en `UPDATE ... FROM`, debe existir siempre una condición del tipo `tabla_objetivo.col = tabla_fuente.col`.

### DELETE

```sql
DELETE FROM schema.table
WHERE condition
RETURNING columns;
```

Mismas reglas que `UPDATE`: sin `WHERE`, vacías la tabla completa.

#### DELETE ... USING (el DELETE con JOIN)

```sql
DELETE FROM marketing.reviews r
USING inventory.products p
WHERE p.id = r.product_id
  AND p.is_active = FALSE;
```

#### DELETE con EXISTS (generalmente más legible)

```sql
DELETE FROM marketing.reviews r
WHERE EXISTS (
    SELECT 1
    FROM inventory.products p
    WHERE p.id = r.product_id
      AND p.is_active = FALSE
);
```

Ya conoces `EXISTS` del Día 3. En DML, `EXISTS` es la forma más legible de borrar condicionado a otra tabla, y suele planear igual o mejor que `USING`. Ambas son válidas; sé consistente con el estilo del equipo.

### Foreign Keys: lo que el motor hace por ti (y contra ti)

Nuestro schema tiene los 3 comportamientos clásicos:

| Acción FK | Ejemplo en DataMartX | Comportamiento al borrar el padre |
|-----------|----------------------|-----------------------------------|
| `ON DELETE RESTRICT` | `sales.orders.customer_id → core.customers` | **Bloquea** el DELETE si existen órdenes. Error. |
| `ON DELETE CASCADE` | `sales.order_items.order_id → sales.orders` | Borra los hijos **automáticamente** junto con el padre. |
| `ON DELETE SET NULL` | `sales.orders.employee_id → hr.employees` | Pone la FK hija en `NULL` y permite el borrado. |

**Implicaciones profesionales:**

1. Borrar un cliente con órdenes **fallará** (`RESTRICT`). Esto es intencional: protege el historial financiero. Si el negocio quiere "eliminar" clientes, la respuesta correcta casi siempre es **soft delete** (`is_active = FALSE`), no `DELETE`.
2. Borrar una orden borra en cascada sus `order_items`. ¿Es lo que quieres? El CASCADE es cómodo y peligroso a la vez: un solo `DELETE` puede arrastrar miles de filas de otras tablas. Antes de un `DELETE` sobre una tabla padre, **cuenta cuántos hijos arrastrará**.
3. Borrar un empleado pone `employee_id = NULL` en sus órdenes. El historial sobrevive, pero pierdes la trazabilidad de quién vendió. Por eso HR usa soft delete (`is_active`).

### Los triggers de esta base de datos: DML nunca es gratis

En DataMartX, tu DML dispara efectos secundarios reales (los revisaremos a fondo en Fase 2, pero hoy debes saber que existen):

1. **`updated_at` automático:** todas las tablas tienen un trigger `BEFORE UPDATE` que pisa `updated_at = CURRENT_TIMESTAMP`. No necesitas (ni debes) setearlo manualmente.
2. **Auditoría (`audit.logs`):** `inventory.products`, `hr.employees` y `sales.orders` registran **todo** INSERT/UPDATE/DELETE con los valores viejos y nuevos en JSONB. Cada `UPDATE` a estas tablas escribe una fila extra por fila modificada. Un `UPDATE` masivo a `sales.orders` no solo toca `orders`: **duplica trabajo en `audit.logs`**.
3. **Archivado de borrados (`audit.deleted_rows`):** borrar de `core.customers`, `sales.orders` o `sales.order_items` copia la fila completa a un archivo antes de eliminarla físicamente.

**Mentalidad profesional:** antes de un DML masivo, pregunta "¿qué triggers tiene esta tabla?". Un `UPDATE` de 500K filas sobre una tabla con trigger de auditoría por fila puede tardar 10x más y llenar el WAL.

### Transacciones: tu red de seguridad

```sql
BEGIN;  -- Nada de lo que sigue es permanente hasta el COMMIT

UPDATE inventory.products
SET price = ROUND(price * 1.08, 2)
WHERE category_id = 5
RETURNING id, sku, price;

-- Validas la salida. ¿Son las filas correctas? ¿Los valores tienen sentido?
-- Si NO:  ROLLBACK;  → la base queda exactamente como estaba
-- Si SÍ:  COMMIT;    → los cambios se vuelven permanentes y visibles
```

**Detalles que separan al profesional del amateur:**

- Mientras tu transacción está abierta, **tus locks están activos**. Otros procesos que intenten tocar esas filas se bloquean. No abras un `BEGIN` y te vayas a almorzar.
- Un error dentro de una transacción la deja en estado abortado: todo lo anterior se descarta y debes hacer `ROLLBACK`.
- Para los ejercicios de hoy: **trabaja siempre dentro de `BEGIN` y termina con `ROLLBACK`**, para no destruir el dataset del curso. El `COMMIT` solo si el ejercicio lo pide explícitamente.

### Soft Delete vs Hard Delete

| | Soft Delete (`is_active = FALSE`) | Hard Delete (`DELETE`) |
|---|---|---|
| Recuperable | Sí, trivial (`UPDATE` inverso) | Solo con backup/archive |
| Historial | Se conserva íntegro | Se pierde (o se archiva) |
| FK RESTRICT | No aplica, no hay conflicto | Bloquea el borrado |
| Costo | Datos "muertos" ocupan espacio e índices | Libera espacio |
| Riesgo | Queries que olvidan `WHERE is_active` inflan métricas | Irreversible |

En DataMartX, `customers`, `employees` y `products` tienen `is_active` por diseño. **La convención de la empresa es soft delete para entidades de negocio, hard delete solo para datos transitorios o purgas planificadas.** Respétala.

### Performance en DML masivo

1. **HOT updates y bloat:** en Postgres, un `UPDATE` es internamente un `DELETE` + un `INSERT` (MVCC). La fila vieja queda como "dead tuple" hasta que `VACUUM` la limpie. Actualizaciones masivas frecuentes inflan la tabla (bloat) y degradan todo.
2. **Batches:** para actualizar millones de filas, hazlo en lotes por rango de PK (ej. 10K-50K filas por transacción) en lugar de un solo `UPDATE` monstruo que lockee media tabla y reviente el WAL.
3. **Índices:** el `WHERE` de tu DML usa índices igual que un `SELECT`. Un `UPDATE` con `WHERE` sobre una columna sin índice hace full scan **y** mantiene locks durante todo el scan.
4. **`TRUNCATE` ≠ `DELETE`:** `TRUNCATE` vacía la tabla entera instantáneamente (no escanea filas, no dispara triggers de fila, resetea espacio). Es DDL, no respeta FKs salvo que uses `CASCADE`, y aunque es transaccional en Postgres, no hay `WHERE`. Úsalo solo cuando realmente quieres vaciar todo.

## 3. Mentalidad de Data Engineer

### Cómo piensa un profesional antes de tocar datos

**1. El ritual pre-DML (no es opcional)**

Junior: escribe el `UPDATE` y lo ejecuta.

Staff:
```
Paso 1: SELECT con el mismo WHERE → ¿cuántas filas? ¿son las correctas?
Paso 2: SELECT COUNT(*) → ¿el número coincide con lo que el ticket espera?
Paso 3: BEGIN
Paso 4: UPDATE ... RETURNING → comparo filas afectadas vs paso 2
Paso 5: Validación post-cambio (agregados, constraints de negocio)
Paso 6: COMMIT o ROLLBACK
```

Si el `COUNT` del paso 2 y las filas del paso 4 no coinciden, algo cambió entre medio (otra sesión, condición no determinista) → `ROLLBACK` e investiga.

**2. Piensa en el blast radius antes que en la lógica**

La pregunta no es "¿cómo actualizo el precio?" sino "¿qué pasa si mi `WHERE` está mal?". Diseña el `WHERE` para que incluso fallando, el daño sea mínimo. Por eso preferimos condiciones sobre PKs o rangos acotados, no condiciones "creativas".

**3. El DML forma parte de un sistema, no es una sentencia aislada**

Antes de tocar `sales.orders` un Staff pregunta: ¿qué triggers tiene? (auditoría). ¿Qué FKs apuntan a ella? (`order_items` en CASCADE, `payments`, `shipments`, `invoices` en RESTRICT). ¿Qué vistas la leen? ¿Hay procesos ETL corriendo ahora mismo que la leen? El `UPDATE` es una línea; el impacto es sistémico.

**4. Idempotencia: ¿puedo correr esto dos veces?**

```sql
-- NO idempotente: correrlo dos veces duplica el descuento
UPDATE inventory.products SET price = price * 0.9 WHERE category_id = 5;

-- Idempotente: correrlo N veces deja el mismo resultado
UPDATE inventory.products SET price = 89.99 WHERE sku = 'ELEC-LAP-001';
```

Los pipelines profesionales se diseñan para que re-ejecutarlos no corrompa datos. Cuando escribas DML, pregúntate: "si esto corre dos veces por un retry, ¿qué pasa?".

**5. Soft delete por defecto, hard delete con justificación**

Borrar es una decisión de negocio, no técnica. El Staff pregunta: "¿legal/finanzas/auditoría necesitan este rastro?". En duda: `is_active = FALSE`. El hard delete se reserva para purgas aprobadas y documentadas (y esta base archiva en `audit.deleted_rows` precisamente por eso).

## 4. Ejemplos Prácticos

Todos los ejemplos asumen el patrón transaccional. En tu sesión de práctica, reemplaza `COMMIT` por `ROLLBACK` para no alterar el dataset.

### Ejemplo 1: Ajuste de precios con validación completa (básico)

```sql
-- Objetivo: Marketing negoció con el proveedor 'TechSupply Co' una baja de
-- costos y quiere reflejar un -5% en el precio de sus productos activos.
-- Validamos antes, ejecutamos en transacción, verificamos después.

-- PASO 1: dry-run. ¿Cuántas filas y cuáles?
SELECT p.id, p.sku, p.name, p.price, ROUND(p.price * 0.95, 2) AS new_price, p.cost
FROM inventory.products p
JOIN core.suppliers s ON s.id = p.supplier_id
WHERE s.name = 'TechSupply Co'
  AND p.is_active = TRUE;

-- PASO 2: sanity check de negocio: ¿algún producto quedaría con price < cost?
-- (violaría chk_price_greater_than_cost y haría fallar TODO el UPDATE)
SELECT COUNT(*) AS would_violate
FROM inventory.products p
JOIN core.suppliers s ON s.id = p.supplier_id
WHERE s.name = 'TechSupply Co'
  AND p.is_active = TRUE
  AND ROUND(p.price * 0.95, 2) < p.cost;

-- PASO 3: ejecución transaccional
BEGIN;

UPDATE inventory.products p
SET price = ROUND(p.price * 0.95, 2)
FROM core.suppliers s
WHERE s.id = p.supplier_id
  AND s.name = 'TechSupply Co'
  AND p.is_active = TRUE
RETURNING p.id, p.sku, p.price;

-- PASO 4: validación post-cambio: la auditoría registró todo (products tiene trigger)
SELECT COUNT(*) AS audit_rows
FROM audit.logs
WHERE table_name = 'inventory.products'
  AND action = 'UPDATE'
  AND logged_at >= CURRENT_DATE;

COMMIT;  -- En práctica: ROLLBACK;
```

**Análisis:**
- Dry-run con el `SELECT` equivalente antes de tocar nada.
- Validación previa contra la constraint `chk_price_greater_than_cost`: previene que el `UPDATE` entero falle a mitad de camino.
- `UPDATE ... FROM` con la condición de unión `s.id = p.supplier_id` (sin cross join).
- `RETURNING` como evidencia inmediata.
- Verificación del rastro en `audit.logs`: en esta base, auditar tu propio DML es parte del trabajo.

### Ejemplo 2: Recalcular segmento de clientes según comportamiento real (intermedio)

```sql
-- Objetivo: El equipo de CRM quiere reclasificar el segmento de clientes
-- según su gasto real de los últimos 12 meses:
--   >= $10,000  → 'Premium'
--   >= $2,000   → 'Standard'
--   <  $2,000   → 'Occasional'
-- Solo clientes activos. Combina CTE (Día 5) + agregación + UPDATE ... FROM.

BEGIN;

WITH customer_spend AS (
    SELECT
        o.customer_id,
        SUM(o.net_amount) AS spend_12m
    FROM sales.orders o
    WHERE o.status NOT IN ('Cancelled', 'Returned')
      AND o.order_date >= CURRENT_DATE - INTERVAL '12 months'
    GROUP BY o.customer_id
),
resegmentation AS (
    SELECT
        customer_id,
        CASE
            WHEN spend_12m >= 10000 THEN 'Premium'::core.segment_enum
            WHEN spend_12m >= 2000  THEN 'Standard'::core.segment_enum
            ELSE 'Occasional'::core.segment_enum
        END AS new_segment
    FROM customer_spend
)
UPDATE core.customers c
SET segment = r.new_segment
FROM resegmentation r
WHERE r.customer_id = c.id
  AND c.is_active = TRUE
  AND c.segment <> r.new_segment  -- solo filas que realmente cambian
RETURNING c.id, c.segment AS new_segment;

-- ¿Cuántos cambios hubo? El RETURNING ya lo dijo, pero validemos distribución:
SELECT segment, COUNT(*)
FROM core.customers
WHERE is_active = TRUE
GROUP BY segment
ORDER BY segment;

COMMIT;  -- En práctica: ROLLBACK;
```

**Análisis:**
- La condición `c.segment <> r.new_segment` evita **updates innecesarios**: filas que ya tenían el segmento correcto no se tocan. Menos dead tuples, menos bloat, menos filas en `audit.logs`. Este detalle es firma de senior.
- El `CASE` castea a `core.segment_enum` porque el CASE devuelve texto y la columna es enum — Postgres exige el cast explícito aquí.
- Clientes sin compras en 12 meses no aparecen en `customer_spend` → no se actualizan. Decisión de diseño explícita: solo reclasificamos con evidencia. ¿Es lo que CRM quiere? Eso se aclara en el ticket **antes** de escribir el SQL.
- Reutiliza patrones de días anteriores (CTE, agregación, filtro de fechas con `INTERVAL`).

### Ejemplo 3: Purgar reseñas huérfanas de productos descontinuados con archivado verificado (avanzado)

```sql
-- Objetivo: Productos descontinuados hace más de 1 año acumulan reseñas que
-- ya no aportan valor analítico. Data Governance aprueba borrarlas, pero
-- exige: (1) conteo previo, (2) evidencia de borrado, (3) verificación de
-- que no queden reseñas huérfanas. Todo en UNA transacción.

BEGIN;

-- Conteo previo dentro de la misma transacción (lo que ves es lo que borras)
SELECT COUNT(*) AS to_delete
FROM marketing.reviews r
JOIN inventory.products p ON p.id = r.product_id
WHERE p.is_active = FALSE
  AND p.updated_at < CURRENT_DATE - INTERVAL '1 year';

DELETE FROM marketing.reviews r
USING inventory.products p
WHERE p.id = r.product_id
  AND p.is_active = FALSE
  AND p.updated_at < CURRENT_DATE - INTERVAL '1 year'
RETURNING r.id, r.product_id, r.rating;

-- Verificación post-delete: no debe quedar ninguna
SELECT COUNT(*) AS orphans_remaining
FROM marketing.reviews r
JOIN inventory.products p ON p.id = r.product_id
WHERE p.is_active = FALSE
  AND p.updated_at < CURRENT_DATE - INTERVAL '1 year';
-- Esperado: 0

COMMIT;  -- En práctica: ROLLBACK;
```

**Análisis:**
- Conteo previo **dentro de la transacción**: en `READ COMMITTED` (default de Postgres), dos `SELECT` fuera de transacción pueden ver datos distintos si alguien inserta entre medio. Dentro de la transacción, el conteo y el `DELETE` son consistentes entre sí (misma "verdadera" ventana si no hay concurrencia; si la hay, el `RETURNING` te da la verdad final).
- `RETURNING` en el `DELETE` materializa exactamente qué se fue — es tu evidencia para Data Governance.
- Verificación post-delete en la misma transacción: si `orphans_remaining > 0`, haces `ROLLBACK` y escales el incidente sin haber dañado nada.
- Nota arquitectónica: `marketing.reviews` no tiene trigger de archivado, así que este borrado **no** queda en `audit.deleted_rows`. Un Staff lo sabe mirando el schema antes de prometer "recuperabilidad" a Governance. Por eso el `RETURNING` se guarda.

## 5. Code Review: Consulta de Junior vs Profesional

### Contexto del ticket

> **FIN-1188**: "Hubo un error de integración: las órdenes del 15 de marzo que pagaron con 'Gift Card' quedaron con status 'Pending' aunque el pago sí se procesó. Actualizar esas órdenes a status 'Processing'."

### Consulta del Junior

```sql
UPDATE sales.orders
SET status = 'Processing'
WHERE order_date = '2025-03-15';
```

### Análisis del Junior

**Puntuación: 1/10. Esto es un incidente de seguridad de datos con patas.**

1. **`order_date = '2025-03-15'` no matchea casi nada... o peor:** `order_date` es `TIMESTAMPTZ`. Compararlo con un literal de fecha compara contra medianoche UTC exacta. Si por casualidad alguna orden cayó a las 00:00:00 UTC, se actualiza; el resto no. El junior verá "UPDATE 3" y pensará "listo", dejando el incidente sin resolver (Día 8: zonas horarias).
2. **No filtra por método de pago:** el ticket dice "que pagaron con Gift Card". Este `UPDATE` tocaría **todas** las órdenes del día, incluidas las de tarjeta que legítimamente siguen pendientes por antifraude. Acaba de inventarse datos en producción.
3. **No filtra por status actual:** pisa cualquier status. Si una orden del día ya estaba 'Cancelled', la "resucita" a 'Processing'. Corrupción de estado de negocio.
4. **Sin transacción, sin dry-run, sin RETURNING, sin COUNT previo:** cero red de seguridad. En una mesa de incidentes, esto se llama "hacer el incidente más grande".
5. **Ignora el trigger de auditoría:** cada fila tocada escribe en `audit.logs`. Un blast radius grande hubiera sido ruido masivo en la auditoría — otro síntoma que el junior ni siquiera sabía que existía.

### Versión Profesional

```sql
-- PASO 1: dry-run. ¿Qué órdenes cumplen exactamente el criterio del ticket?
SELECT o.id, o.order_date, o.status, p.payment_method, p.status AS payment_status
FROM sales.orders o
JOIN sales.payments p ON p.order_id = o.id
WHERE (o.order_date AT TIME ZONE 'America/Mexico_City')::DATE = '2025-03-15'
  AND p.payment_method = 'Gift Card'
  AND p.status = 'Completed'      -- el pago SÍ se procesó (evidencia)
  AND o.status = 'Pending';       -- solo las afectadas por el bug

-- PASO 2: ejecutar en transacción con el WHERE exactamente validado
BEGIN;

UPDATE sales.orders o
SET status = 'Processing'
FROM sales.payments p
WHERE p.order_id = o.id
  AND (o.order_date AT TIME ZONE 'America/Mexico_City')::DATE = '2025-03-15'
  AND p.payment_method = 'Gift Card'
  AND p.status = 'Completed'
  AND o.status = 'Pending'
RETURNING o.id, o.status;

-- PASO 3: comparar filas del RETURNING contra el COUNT del dry-run.
-- PASO 4: verificación post-cambio: no deben quedar afectadas
SELECT COUNT(*) AS still_broken
FROM sales.orders o
JOIN sales.payments p ON p.order_id = o.id
WHERE (o.order_date AT TIME ZONE 'America/Mexico_City')::DATE = '2025-03-15'
  AND p.payment_method = 'Gift Card'
  AND p.status = 'Completed'
  AND o.status = 'Pending';
-- Esperado: 0

COMMIT;
```

**Mejoras:**
1. **Fecha en zona horaria del negocio** (Día 8 aplicado a DML): el "15 de marzo" del negocio, no del servidor.
2. **Join con `payments` y doble evidencia:** `payment_method = 'Gift Card'` **y** `p.status = 'Completed'`. El criterio del ticket, literal y verificable.
3. **`o.status = 'Pending'`:** solo toca órdenes en el estado exacto que describe el bug. Idempotente: correrlo dos veces, la segunda afecta 0 filas.
4. **Ritual completo:** dry-run → transacción → `RETURNING` → verificación post → commit.
5. **Blast radius conocido y mínimo:** si el `WHERE` estuviera mal, el dry-run lo revela antes del daño.

## 6. Errores Frecuentes

### Error 1: UPDATE/DELETE sin WHERE

```sql
-- CATASTRÓFICO: actualiza TODA la tabla
UPDATE inventory.products SET price = price * 1.1;

-- CORRECTO: WHERE explícito, siempre
UPDATE inventory.products SET price = price * 1.1
WHERE category_id = 5;
```

**Prevención profesional:** si realmente necesitas toda la tabla, escribe `WHERE TRUE` explícitamente. Ese "ruido" sintáctico obliga al reviewer (y a tu yo del futuro) a confirmar que fue intencional.

### Error 2: Cross join accidental en UPDATE ... FROM

```sql
-- MAL: cada fila recibe el valor de una fila ARBITRARIA de employees
UPDATE sales.orders o
SET employee_id = e.id
FROM hr.employees e
WHERE o.employee_id IS NULL;

-- BIEN: condición de unión entre objetivo y fuente
UPDATE sales.orders o
SET employee_id = e.id
FROM hr.employees e
WHERE o.employee_id IS NULL
  AND e.id = 42;  -- fuente acotada y determinista
```

### Error 3: Violar constraints calculadas por actualizar en dos pasos

```sql
-- FALLA: chk_net_amount exige net = total - discount en la misma fila
UPDATE sales.orders SET total_amount = 500 WHERE id = 100;

-- BIEN: una sola sentencia, constraint satisfecha
UPDATE sales.orders
SET total_amount = 500,
    net_amount = 500 - discount_amount
WHERE id = 100;
```

### Error 4: DELETE chocando con RESTRICT por no revisar los hijos

```sql
-- ERROR: el cliente tiene órdenes (orders.customer_id es RESTRICT)
DELETE FROM core.customers WHERE id = 777;

-- BIEN: decisión de negocio informada → soft delete
BEGIN;
UPDATE core.customers
SET is_active = FALSE
WHERE id = 777
RETURNING id, is_active;
COMMIT;
```

### Error 5: Olvidar que los CASCADE multiplican el borrado

```sql
-- Borrar 1 orden arrastra sus order_items (CASCADE). ¿Cuántos son?
-- Siempre contar el impacto total antes:
SELECT 
    (SELECT COUNT(*) FROM sales.orders WHERE id = 100) AS orders_to_delete,
    (SELECT COUNT(*) FROM sales.order_items WHERE order_id = 100) AS items_cascaded;
```

### Error 6: Comparar timestamps con fechas en el WHERE del DML

```sql
-- MAL: solo matchea medianoche UTC exacta
UPDATE sales.orders SET status = 'Processing'
WHERE order_date = '2025-03-15';

-- BIEN: fecha local del negocio
UPDATE sales.orders SET status = 'Processing'
WHERE (order_date AT TIME ZONE 'America/Mexico_City')::DATE = '2025-03-15'
  AND status = 'Pending';
```

### Error 7: UPDATE masivo en una sola transacción

```sql
-- RIESGO: 400K locks, WAL enorme, tabla bloqueada minutos
UPDATE sales.orders SET status = status WHERE id > 0;

-- BIEN: batches por rango de PK
BEGIN;
UPDATE sales.orders SET status = status
WHERE id BETWEEN 1 AND 50000;
COMMIT;
-- repetir con el siguiente rango
```

### Error 8: Confiar en "lo probé en dev" sin validar volumen real

El `WHERE` que en dev toca 10 filas en producción puede tocar 10M. El dry-run con `COUNT(*)` se hace **en el entorno destino**, no en tu laptop.

## 7. Resumen

### Conceptos Clave

1. **El DML es irreversible sin red de seguridad:** dry-run → `BEGIN` → ejecutar → validar → `COMMIT`/`ROLLBACK`. Este ritual no es burocracia, es lo que te deja dormir tranquilo.
2. **`RETURNING` es tu evidencia:** en `UPDATE` y `DELETE` te devuelve exactamente lo que cambió. Guárdalo.
3. **`UPDATE ... FROM` y `DELETE ... USING`/`EXISTS`:** la forma de hacer DML con joins. Siempre con condición de unión entre objetivo y fuente, o tendrás un cross join silencioso.
4. **Las constraints te protegen (y te detienen):** `CHECK`, FK, dominios y enums validan cada fila. Diseña el DML para satisfacerlas en una sola sentencia.
5. **Los FK deciden tu estrategia de borrado:** `RESTRICT` bloquea, `CASCADE` arrastra, `SET NULL` desconecta. Conócelos antes de borrar.
6. **Tu DML dispara triggers:** `updated_at` automático, auditoría en `products`/`employees`/`orders`, archivado en `customers`/`orders`/`order_items`. El costo real de un DML incluye sus efectos.
7. **Soft delete para entidades de negocio, hard delete solo con aprobación:** en DataMartX, `is_active = FALSE` es la convención.
8. **Idempotencia:** un DML profesional puede re-ejecutarse sin corromper datos.

### Tabla de Referencia Rápida

| Tarea | Sintaxis |
|-------|----------|
| Update simple | `UPDATE t SET c = v WHERE cond RETURNING ...` |
| Update con join | `UPDATE t SET c = v FROM otra o WHERE o.id = t.fk AND ...` |
| Delete simple | `DELETE FROM t WHERE cond RETURNING ...` |
| Delete con join | `DELETE FROM t USING otra o WHERE o.id = t.fk AND ...` |
| Delete con EXISTS | `DELETE FROM t WHERE EXISTS (SELECT 1 FROM otra o WHERE ...)` |
| Patrón seguro | `BEGIN; ...validar...; COMMIT;` (o `ROLLBACK;`) |
| Soft delete | `UPDATE t SET is_active = FALSE WHERE ...` |
| Vaciar tabla | `TRUNCATE t;` (solo si es intencional) |

### Reglas de Oro

1. **Nunca** DML sin dry-run previo con el mismo `WHERE`.
2. **Nunca** DML fuera de transacción en trabajo manual.
3. **Siempre** `RETURNING` + validación post-cambio.
4. **Siempre** condición de unión en `UPDATE ... FROM`.
5. Revisa **FKs y triggers** de la tabla antes de tocarla.
6. Filtra por el **estado actual esperado** (idempotencia).
7. DML masivo → **batches** por rango de PK.
8. En esta base de práctica: **termina con `ROLLBACK`** salvo indicación contraria.
